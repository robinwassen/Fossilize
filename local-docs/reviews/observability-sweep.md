# Observability and diagnosis sweep

27 October 2026 · Source revision `556da9ff7d7616704dda515756219ab1dab693ec` · Research and proposed work only. Updated with mandatory automated acceptance criteria for all 24 tasks; these tests are not yet implemented.

## Recommendation

Start by repairing lost outcomes at their source, then propagate them through workers and controllers, and only then make the final report authoritative. More log lines alone cannot satisfy the standard. In particular, neither a drained queue, a clean child exit, the existing progress counters, nor the replayer-cache marker currently proves successful required work.

The ordered backlog below starts with inexpensive, independently useful fixes. Later steps depend on earlier evidence becoming available. Each step includes a bounded implementation target and adversarial acceptance criteria. Steps marked M should be split at the indicated boundary when needed; these are relative scopes, not time estimates. A sequential implementation may follow the numbering exactly; dependency lists identify the actual prerequisites. Permanent `FOS-` keys identify items across files and reordering; numbers only express the current sequence. Allocations are recorded in the [project-wide key registry](../backlog-keys.md).

## Ordered implementation backlog

All criteria below are mandatory completion gates for the applicable implementation slice. They describe future assertions, not tests already implemented or passing. A task is complete only when its criteria are covered by committed automated tests registered with the project test runner/CI, and passing evidence records the commands, configurations and platforms. If a task is split, each split-out item must receive its own registered key and name its covered criteria; the parent remains incomplete until all are satisfied. Manual inspection, log screenshots and the observation-only research runner are insufficient acceptance evidence.

Use unit tests for result/state logic and deterministic fault injection, plus subprocess/filesystem/IPC/layer integration tests for externally visible behavior. Assert returned outcomes, exit statuses, structured fields, actual output contents and handle/application behavior; prose-only assertions are appropriate only where human presentation itself is the requirement. Include successful controls alongside failure cases. Upgrade E1–E9 into assertion-bearing regressions as their owning tasks are implemented. Tests must expose the defect before its fix where feasible, rather than merely mirror implementation internals.

Concurrency/deadline tests must use fake clocks, barriers and controllable adapters instead of random driver instability or fragile sleeps. Give process tests watchdogs and isolated temporary output directories. Linux and Windows process changes require platform-specific automated evidence; GPU-independent mocks are the baseline, with hardware jobs for hardware claims. An unavailable platform/device is skipped/unverified and leaves that acceptance criterion open. Record applicable debug/release and exception-enabled/disabled coverage; use sanitizer jobs where useful for changed parsing, lifetime or concurrency code. Tests must check honest unknown outcomes where evidence is deliberately lost.

**Compatibility gate for every affected public boundary:** declare whether source, binary, protocol and behavioral compatibility are preserved or intentionally changed. Maintain compile/run fixtures for preserved old callers/invocations, schema/protocol fixtures for preserved consumers and prebuilt-consumer checks only where binary compatibility is claimed. Assert and document intentional changes, including formerly false-success CLI exits. Additive signatures alone do not establish compatibility; do not claim that all existing callers continue working. Require structured outcomes without prose parsing once the relevant result API/mode is introduced.

## Dependency and delivery notes

The critical path is **FOS-000005 → FOS-000009 → (FOS-000010 and FOS-000011) → FOS-000012 → FOS-000013 → FOS-000014**: worker facts precede reconciliation, which precedes a trustworthy controller/API result. **FOS-000003 → FOS-000016 → FOS-000017 → FOS-000019** is the persistence/capture path. **FOS-000006** prevents later runs from trusting a failed attempt. **FOS-000004** is an early containment fix, not a substitute for the richer accounting. Initial result schemas may report persistence/support detail as unknown until the respective producers are migrated; they must not imply whole-standard compliance early.

Keep regression verification alongside every iteration. Do not defer all tests to `FOS-000024`. The highest-value fixtures are E1–E9, deterministic worker failure/deadline injection, duplicate/stale messages, full diagnostic rings, close-time ENOSPC, optional versus required output loss, and cancellation before/after final publication. Linux and Windows process implementations need the same behavioral matrix even when mechanisms differ. Apple/Android builds use `NO_ROBUST_REPLAYER`; ordinary replay/library/capture contracts still apply without inventing worker support there.

## Adversarial recheck and rejected shortcuts

This was a self-adversarial code and probe review, not an independent reviewer or sub-agent audit. The retained reproduction runner was then executed from a fresh directory: all 13 case exit statuses reproduced, the recorder/file-helper observations matched exactly, and the existing system test again returned 0. Source-reference targets were checked against the current files. For each material finding I checked the caller, alternative modes and possible existing evidence before proposing work.

| Challenge | Rechecked evidence / resulting constraint |
|---|---|
| “Progress counters and crash hashes already solve this.” | They exist and are useful. E6 still returns zero. Counters are partly optional, skips mix causes, retries duplicate activity and the ring is lossy. Keep them; add an authoritative outcome. |
| “Every child failure should make the run fail forever.” | Rejected. Recovery can satisfy the full contract. Separate failed attempts from final items; skipped required culprits/unknown ranges prevent success unless explicitly excluded. |
| “Fix controller exits and replay is done.” | Rejected. E7 has clean process exits after controlled parse rejection; void creation routines lose Vulkan failures. Worker producers must change too. |
| “The crash fixture merely exposes an assertion, not a real bug.” | It does expose an unchecked Fossilize schema boundary. E7 separately reproduces false success without assertions, and E5 proves controller behavior after worker loss. No driver crash was claimed. |
| “A warning about truncation is sufficient; fail all truncated captures.” | Rejected as a blanket policy. Stream salvage is intentional. Return its scope/completeness and let explicit policy define whether the salvaged prefix satisfies the requested operation. |
| “Any failed optimization or error-level log means failure.” | Rejected. A documented original-module fallback can satisfy a copy/transform policy. Severity and operation success must remain separate. |
| “Buffered fwrite success proves output is safe.” | E3/E4 disprove close completion; even checked close does not prove power-loss durability or driver cache reuse. |
| “Replay-cache entries are proven compiled pipelines.” | Creation dispatch writes markers without checking creation success. Marker membership proves membership under the old producer behavior, not durable compilation. No real-driver reproduction was claimed. |
| “Turn on more logs or adopt OpenTelemetry first.” | Rejected. Neither repairs discarded return values, close errors, causality or coverage. No SDK, remote collector or upload is required. |
| “Guarantee a final result from every crash.” | Rejected. Signal safety, SIGKILL, blocked storage and torn writes constrain delivery. Missing final evidence is incomplete/unknown. |
| “Wrap a callback and guarantee it never blocks.” | Rejected. Arbitrary synchronous code cannot be safely interrupted. Use documented sink constraints or bounded queued delivery and truthful diagnostic-loss reporting. |
| “This proves the original Steam cache-loss theory.” | Rejected. These probes use no GPU and do not measure Steam scheduling, driver-cache durability or reuse. They establish Fossilize outcome propagation defects. |
