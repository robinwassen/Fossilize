# Worker lifecycle audit rules

Research date: 2026-10-29. Read project descriptor, pillars and verification guidance. These are OS facts and review criteria, not findings about Fossilize. No repository modifications.

## OS facts: requirements that implementation must respect

1. **Parent death is thread scoped on Linux.** `PR_SET_PDEATHSIG` observes the creating thread, so a launcher-thread return can terminate a child while the rest of the application remains alive. It is reset in children of fork and retained across ordinary exec, but credential/capability transitions can clear it. Registration is not retroactive if the parent already died; recheck expected parent after registration. Each process edge requires its own protection. Source: https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html . Scope of a parent-PID check must match actual ownership; it does not convert thread-scoped death into process-scoped death.

2. **Fork does not duplicate sibling threads.** After fork in a multithreaded program, the child retains copies of locks and state but only the calling thread; before exec, restrict child actions to async-signal-safe operations or prove a safe alternative protocol. Merely not creating threads in the library does not prove its host application is single threaded. Source: https://man7.org/linux/man-pages/man2/fork.2.html . Signal handlers likewise require async-signal-safe functions; malloc, stdio and arbitrary driver cleanup are not generally safe there: https://man7.org/linux/man-pages/man7/signal-safety.7.html . Unsafe code is an implementation-contract violation/risk, but a deadlock requires a concrete held-lock/interruption scenario to claim observed impact.

3. **Exit must be collected.** An exited child remains a zombie until waited for, absent automatic-reap policy. WNOHANG zero means no changed child state; EINTR is retryable and ECHILD differs from successful exit. Threads in a process can wait for children created by other threads, so competing waiters need coordination. Source: https://man7.org/linux/man-pages/man2/waitpid.2.html . Do not read WEXITSTATUS before WIFEXITED or WTERMSIG before WIFSIGNALED. Reaping failure is not evidence the child still computes.

4. **FD ownership determines EOF and liveness.** A pipe reader sees EOF only after all write references are closed; extra inherited writers can suppress EOF forever. A full blocking pipe stalls its writer, so supervisors must drain child output without blocking all lifecycle control. Close irrelevant references in each fork branch. Source: https://man7.org/linux/man-pages/man7/pipe.7.html . Unmarked descriptors survive exec by default, while signal masks are retained and caught handlers reset: https://man7.org/linux/man-pages/man2/execve.2.html . Use an explicit FD inheritance set; CLOEXEC ideally atomic at creation in multithreaded hosts.

5. **Signals have distinct semantics.** SIGKILL/SIGSTOP cannot be caught, blocked or ignored; SIGCONT resumes stopped processes. Standard signals coalesce, and per-thread masks require all eligible threads to cooperate with signalfd/sigwait. Source: https://man7.org/linux/man-pages/man7/signal.7.html . Therefore drain waitable child changes rather than assume one SIGCHLD per death. Suspending is not termination or memory release. Force-kill is not a guarantee of immediate observable exit when kernel work is uninterruptible.

6. **Stable identities improve races but are not mandatory.** pidfd can be polled for process exit and used for signaling/waiting; ordinary PID polling must reason about competing reaping and reuse. Source: https://man7.org/linux/man-pages/man2/pidfd_open.2.html . Absence of pidfd is not itself a defect.

7. **Windows jobs contain processes after association.** Children normally inherit their parent's job unless breakaway rules apply. `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` applies only when the last job handle is closed; inherited/duplicated handles can defeat the expected owner-death effect. Notifications generally are not guaranteed, so query/wait fallback matters. Source: https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects . Check every job creation/configuration/assignment result; assignment can fail, including incompatible existing job contexts: https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject . Create suspended, associate, then resume is a recommended startup containment sequence, not a universal API mandate.

## Design criteria (recommendations derived from the above facts)

- **R1 Ownership:** Explicitly distinguish borrowed/detached execution from owned execution. One authority collects exit and accounts each process once. Define owner object destruction, owner process death, owner thread exit and caller cancellation separately.
- **R2 Transactional startup:** For every acquired FD/handle/map/child, every subsequent failure closes resources, terminates any started execution if owned, and reaps when possible. Spawn success must not imply exec/job-assignment success without a handshake/status path.
- **R3 Monotonic cancellation:** Once cancellation begins, no restart or new work admission. Kill running and stopped children; preserve termination state across delayed messages. Repeated cancellation and racing normal completion must be safe.
- **R4 Bounded phases:** Bound startup, compilation no-progress, crash cleanup, final driver teardown and shutdown independently. An active main-loop heartbeat does not prove useful compiler progress. A watchdog started only after initialization cannot bound initialization.
- **R5 Pause/resume:** Record intentional stopped state; suspend/rearm watchdogs consistently; guarantee a resume or terminal transition. Evaluate watchdog behavior if it expires while stopped, after crash notification, and while shutdown starts.
- **R6 IPC independence:** No blocking bootstrap write, unbounded buffered output, retained writer, malformed message or control-channel closure may prevent ownership/cancellation handling indefinitely. Include EINTR/partial I/O/error cases.
- **R7 Honest completion:** Work-counter completion, child exit, successful output persistence and full requested coverage are separate states. Report failed/unsupported/incomplete distinctly; never treat controller exit alone as complete replay.
- **R8 Recovery:** Replacement requires forward progress or bounded retries. Identify which work failed, avoid replaying it forever, and reject stale messages/timers associated with a previous PID occupying a worker slot.
- **R9 Resource scope:** Allocation failure, process/FD exhaustion and memory pressure must not leave surviving owned workers or untracked resources. Pausing existing allocations is a resource policy, not a hard memory cap.

## Coverage matrix to require from inspectors/checkers

For external launcher, controller, worker and thread pool separately: before first resource; each partial startup failure; fork/CreateProcess failure; exec failure; initialization hang; normal idle/work/finish; intentional pause/resume; external stop/continue; compilation timeout; crash before progress; crash with progress; recovery spawn failure; IPC EOF/error/backpressure; caller object destruction; caller thread exit; caller process normal exit/crash/SIGKILL; controller SIGINT/SIGTERM/SIGKILL; shutdown during restart; cleanup failure; final driver/cache teardown; wait interrupted/competing reap; repeated start/cancel/wait; platform unsupported modes.

Evidence labels: **source-proven** means exact reachable branch plus governing OS semantics; **reproduced** means focused run with assertions and environment; **conditional risk** means prerequisites unproven; **not a defect** covers documented contracts and intended policies; **unavailable/incomplete** identifies platform/test limits. Source proof can establish a bug without recreating a real Steam session; it cannot establish frequency or explain a historical report without matching evidence.
